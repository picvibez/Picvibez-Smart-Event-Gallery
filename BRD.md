# Business Requirements Document (BRD) - PicVibez

This document outlines the business rules, system behaviors, and acceptance criteria for PicVibez (Smart Event Gallery), mapped directly to the Supabase database schema.

| Req ID | Module | Feature / Requirement | Description & Business Logic | Acceptance Criteria & DB Impact |
| :--- | :--- | :--- | :--- | :--- |
| **AUTH-01** | **Auth & Profiles** | **User Registration & Profile Auto-Creation** | Users must be able to sign up via Email or Google. Upon successful authentication, the system must automatically generate a user profile to store application-specific data. | **Pass:** User logs in; a trigger automatically creates a row in the `profiles` table using data from `auth.users`. |
| **AUTH-02** | **Auth & Profiles** | **AI Selfie Registration** | Users must be able to upload a "reference selfie". The system will process this image to generate a facial embedding used for future AI photo matching. | **Pass:** AI generates an embedding and saves it to `profiles.face_embedding_id`. |
| **EVT-01** | **Core Event Engine** | **Event Creation & Default Limits** | A Host can create an event. Newly created events must default to a free tier (e.g., 500MB storage limit) and have watermarks enabled by default. | **Pass:** Row created in `events` table with `storage_limit_bytes` = 536870912 and `is_watermark_enabled` = TRUE. |
| **EVT-02** | **Core Event Engine** | **Role-Based Access Control (RBAC)** | Users joining an event must be assigned a specific role (Host, Photographer, or Guest). Roles dictate permissions (e.g., only Hosts/Photographers can upload without approval; Guests can only view/like). | **Pass:** User is added to `event_participants` table with the correct `participant_role` ENUM. |
| **EVT-03** | **Core Event Engine** | **Album Organization** | Hosts and Photographers must be able to create sub-folders (Albums) within an event (e.g., "Haldi", "Reception") to organize photos. | **Pass:** Row created in `albums` table linked to the parent `event_id`. |
| **BIL-01** | **Billing & Monetization** | **Premium Plan Upgrades** | Hosts can pay to upgrade their event to a Premium Plan. Upgrading must remove watermarks, enable AI tagging, and increase the base storage limit (e.g., to 10GB). | **Pass:** Stripe webhook logs a `base_plan` in `transactions`. System updates `events` table to disable watermarks and increase `storage_limit_bytes`. |
| **BIL-02** | **Billing & Monetization** | **Storage Add-on Purchases** | If an event runs out of storage, the Host can purchase "Storage Add-ons" (e.g., +5GB). The system must dynamically increase the event's total allowed storage. | **Pass:** Stripe webhook logs a `storage_addon` in `transactions`. System adds the purchased bytes to `events.storage_limit_bytes`. |
| **MED-01** | **Media Engine** | **Photo Upload & Size Tracking** | Authorized users can upload photos. The system must record the exact file size in bytes for every photo uploaded to accurately track server costs. | **Pass:** Photo is saved to Supabase Storage. Row is created in `photos` table with accurate `file_size_bytes`. |
| **MED-02** | **Media Engine** | **Automated Storage Quota Enforcement** | The system must automatically calculate the total storage used by an event. If `current_storage_bytes` + new upload size exceeds `storage_limit_bytes`, the upload must be blocked. | **Pass:** DB Trigger automatically updates `events.current_storage_bytes` on photo insert/delete. App blocks upload if limit is exceeded. |
| **MED-03** | **Media Engine** | **Guest Upload Moderation** | Hosts can optionally require approval for photos uploaded by Guests. Unapproved photos remain hidden from the public gallery. | **Pass:** Guest uploads set `photos.is_approved` to FALSE. Host action updates it to TRUE. |
| **MED-04** | **Media Engine** | **Advanced Grid Filtering & Sorting** | Users must be able to filter the main photo grid by Date (Newest/Oldest), Size (Low/High), Type (Photos/Videos), and specific People. | **Pass:** Frontend queries the `photos` table with appropriate `ORDER BY` and `WHERE` clauses based on user selection. |
| **MED-05** | **Media Engine** | **Uploader Attribution (DP Icon)** | Every photo or video in the grid must display a small Display Picture (DP) icon indicating which user uploaded the media. | **Pass:** Frontend joins the `photos` table with the `profiles` table via `uploaded_by` to display the `avatar_url` on the thumbnail. |
| **MED-06** | **Media Engine** | **Dynamic Grid Layout** | Users must be able to dynamically adjust the density of the photo grid (e.g., 3, 4, or 5 columns) to view more or fewer photos at once, potentially via pinch-to-zoom gestures. | **Pass:** Frontend implements a responsive grid system where column count is controlled by user state/gestures. |
| **SMR-01** | **Smart Engine** | **AI Facial Recognition & Tagging** | When a photo is uploaded, the AI must scan it for faces, compare them against registered user embeddings, and automatically tag recognized users. | **Pass:** AI finds a match and inserts a row into the `photo_tags` table with the `photo_id` and `tagged_user_id`. |
| **SMR-02** | **Smart Engine** | **Personalized "Find Me" Feed** | Guests must be able to click a "Find Me" button to instantly see a filtered feed of only the photos they are detected in. | **Pass:** App queries the `photos` table joined with `photo_tags` where `tagged_user_id` matches the current user. |
| **SMR-03** | **Smart Engine** | **Semantic Visual Search** | Users must be able to search for photos using natural language (e.g., "Bride", "Dance", "Red dress"). The system must categorize photos into "People Detected" and "Suggested Moments". | **Pass:** AI generates image embeddings/labels on upload. Frontend queries these labels via a search bar. |
| **SOC-01** | **Social Engine** | **Photo Likes** | Event participants must be able to "Like" photos in the gallery. A user can only like a specific photo once. | **Pass:** Row inserted into `photo_likes`. Composite primary key prevents duplicate likes by the same user. |
| **SOC-02** | **Social Engine** | **Photo Comments** | Event participants must be able to leave text comments on photos to increase engagement. | **Pass:** Row inserted into `photo_comments` with `comment_text`, linked to `photo_id` and `user_id`. |
| **MKT-01** | **Market Engine** | **Vendor Directory & Discovery** | Hosts must be able to browse a directory of event vendors (Photography, Decor, DJ, Catering) directly within the event view. | **Pass:** Frontend fetches data from a new `vendors` table, displaying ratings, pricing, and categories. |
| **MKT-02** | **Market Engine** | **Vendor Search & Filtering** | Users must be able to search for specific vendors and filter them by category (e.g., "Photography", "Decor"). | **Pass:** Frontend queries the `vendors` table using `ILIKE` for search and `WHERE category = X` for filtering. |

### Document Sign-off / Next Steps
*   **Frontend Team:** Use the *Acceptance Criteria* to build UI guards (e.g., disabling the upload button if the storage limit is reached).
*   **Backend/AI Team:** Use the *Smart Engine* requirements to build the Edge Functions that will process images and insert data into the `photo_tags` table.
*   **Database Admin:** The schema provided previously fully satisfies all requirements listed in this BRD, with the addition of a new `vendors` table required for the Market Engine.
